## Lens B — Technical Soundness: NOT CLEAN

- **F-R21-LENSB-01 (MEDIUM, NEW):** The story's downstream `OnAck` call-site was depicted as chained off `deliverDownstream` (per-arrival, dedup-gated) — the Q4 diagram, AC-005, AC-006, Task 6, the BC-2.02.002/BC-2.02.005 Anchors Consumed rows, the Design Constraints `arq.OnAck` call-contract prose, and the Edge Cases duplicate-frame row all depicted this shape. This diverges from the binding placement note, where `OnAck` runs **once per tick, IN THE TICK BODY, after `Send` returns** — structurally decoupled from `deliverDownstream`'s per-arrival dedup gate, not chained off or gated by it.

  Two compounding problems with the story's depicted (wrong) shape:
  1. **Lexical-scope violation.** `deliverDownstream` is invoked per-arrival inside the dedup path; the tick-body-local `chanSeq` variable (computed once per downstream tick, before any per-arrival dispatch) is out of lexical scope inside `deliverDownstream`. A call to `OnAck(chanSeq, ...)` chained off `deliverDownstream` cannot reference the tick-body `chanSeq` without threading it through an additional parameter or closure that the story never specified.
  2. **No source for the value even if threaded.** `multipath.Frame` (the type flowing through `deliverDownstream`'s per-arrival dedup path) carries no `ChanSeq` field. There is no frame-level value to substitute for the tick-body `chanSeq` even if the scoping problem were patched around. The story's depicted structure was therefore **not cleanly implementable** as written — an implementer following the Q4 diagram literally would hit a compile-time-or-later design dead end.

  Upstream (`accessNode.SendKeystroke` inside `deliverUpstream`) was independently re-verified correct and is **not** affected by this finding — only the downstream `OnAck` leg was wrong.
