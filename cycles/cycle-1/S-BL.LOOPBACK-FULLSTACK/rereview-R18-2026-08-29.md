### Lens B — technical-soundness — NOT CLEAN

**NEW finding F-R18-LENSB-01 (MED):** the v1.13 design's upstream `failLoud` placement is unsound against `multipath.Send`'s aggregation semantics. `multipath.Send` (`multipath.go:244-286`) returns `nil` whenever **at least one** selected path's `Sent` is true (`sent >= 1 ⇒ nil`). In the upstream duplicate-and-race dispatch, the dedup sibling path's `deliverUpstream` call always returns `nil` without ever calling `SendKeystroke` — so a check on `upstreamMP.Send`'s return value in the upstream tick body can **never** observe a masked error from the delivering path: whenever the delivering path fails but the dedup sibling reports `Sent=true`, `Send`'s aggregate return is `nil` and the failure is silently swallowed at any post-`Send` check site. The design must pin the `failLoud` check in-place at the `driver.accessNode.SendKeystroke` call site inside `deliverUpstream` itself, not at any point downstream of the aggregated `Send` return.

**NEW finding F-R18-LENSB-02 (LOW):** the §M2 window-safety invariant carries an off-by-one. The v1.13 text states "`chanSeq` at the first data tick equals the number of empty ticks elapsed" (i.e., `chanSeq=E`), but `halfchannel.Tick()` pre-increments `seq` before assigning it to the frame — so the real value at the first data tick is `E+1`, not `E`. This matches AC-016's own worked example (`E=65` empty ticks elapsed → `chanSeq=66` at the boundary), which the prose statement of the invariant contradicts.
