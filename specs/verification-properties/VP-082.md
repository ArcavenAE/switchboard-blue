# VP-082: Access-Node Connector Reconnect Preserves ARQ In-Flight and Session/Console-Authorization State

## Property Statement

∀ transition of the access-node data-plane connector (`internal/accessdial`,
BC-2.04.009) out of its *live* state due to a connection loss (read error,
write error, or explicit remote close), followed by a subsequent successful
reconnect (fresh `net.Dial` + fresh client-side `NODE_IDENTIFY` admission,
per BC-2.04.009 Postconditions 1–3):

1. **ARQ in-flight `SendBuffer` state survives unchanged.** Every sequence
   number that was in-flight (per `arq.ARQ.InFlightContains`) immediately
   before the connection loss is still in-flight, with the identical
   payload retrievable via `arq.ARQ.PayloadForInFlight`, immediately after
   the reconnect completes and before any new frame is sent on the new
   connection. The connector's teardown-and-rebuild of the TCP connection
   and its `NODE_IDENTIFY`-derived envelope (`SrcAddr`/`DstAddr`/`SVTNID`/
   `FrameAuthKey`) does NOT reach into, reset, or reconstruct the
   `arq.ARQ` handle itself.
2. **Session/console-authorization state survives unchanged.** Every
   console attachment and authorization state held by `session.AccessNode`
   (`ConsoleSet` entries, `SessionAuth` grants) that existed immediately
   before the connection loss is still present, unmodified, immediately
   after the reconnect completes. The access node does not detach, evict,
   or re-authorize any console solely because the underlying wire
   connection to the router was torn down and rebuilt.
3. **Only the connection-scoped state is discarded and rebuilt.** The TCP
   `net.Conn` itself and the specific `Envelope{SVTNID, SrcAddr, DstAddr,
   FrameAuthKey}` bound to the OLD connection are discarded; a fresh
   envelope is derived from the NEW admission handshake. This is the only
   state this property permits to change across a reconnect — properties 1
   and 2 bound everything else.

   **Non-vacuity requirement (v1.1 — resolves the story's Residual Open
   Question 2, "`FrameAuthKey` derivation entropy confirmation").** `SVTNID`
   is config-sourced and invariant across reconnects (BC-2.04.009 Design
   Constraints §1); `SrcAddr = frame.DeriveNodeAddress(SVTNID, pubkey)` is a
   PURE, deterministic function of that same invariant `(SVTNID, pubkey)`
   pair (VP-014: "DeriveNodeAddress is deterministic"); `DstAddr` is a fixed
   zero-value placeholder in this story's scope (Non-Goals). This means the
   ONLY component of `Envelope` that could conceivably differ across a
   reconnect of the SAME node is `FrameAuthKey` — and `FrameAuthKey` MUST
   NOT differ. `FrameAuthKey`'s canonical derivation (ARCH-04-admission-security.md
   §Key derivation) is `HKDF-Extract(salt=svtn_id, ikm=node_admission_pubkey)
   → PRK; HKDF-Expand(PRK, info="switchboard-frame-auth", length=32) →
   frame_auth_key` — a function of `(svtn_id, node_admission_pubkey)` ONLY,
   with NO handshake-specific entropy (no nonce, no timestamp, no per-session
   salt). This is architecture-wide, already-shipped precedent, not a design
   choice this BC gets to make: BC-2.05.010 §"FrameAuthKey and NodeAddr are
   derived, not stored" states `FrameAuthKey` is "derived deterministically
   from `(svtnID, pubkey)`" on every load, and the router independently
   recomputes the identical key via the same formula (it is never transmitted
   after admission — ARCH-04 §"Key distribution" describes an `ADMITTED`
   message carrying the key that predates and is superseded by BC-2.01.009's
   shipped three-message handshake, which has no fourth message; both sides
   MUST derive the same key independently with no side channel). If
   `FrameAuthKey` were salted with handshake-specific entropy (e.g. the
   `Challenge.Nonce`), the router's independently-computed, forwarding-table-
   cached `FrameAuthKey` (BC-2.05.008) would silently mismatch the
   connector's own value on every reconnect, breaking HMAC frame
   verification for the access node until some undefined re-synchronization
   step ran — a protocol design this BC does not specify and the codebase
   does not have. **Therefore: `Envelope{SVTNID, SrcAddr, DstAddr,
   FrameAuthKey}` is expected to be BYTE-IDENTICAL before and after a
   reconnect of the same node identity** (same keypair, same configured
   `SVTNID`). This is what makes reconnect resilient without a live
   key-exchange step — see Test Scenario 3 below for how this property is
   proven without asserting a false value-inequality.

This property enforces BC-2.04.009 Postcondition 7 verbatim ("a transition
out of *live* does NOT reset the `arq.ARQ` in-flight `SendBuffer` state, nor
the access node's session/console-authorization state — only the TCP
connection and its envelope are torn down and rebuilt"). It closes the open
question named in `S-BL.RESYNC-FRAME-placement-note.md` §7.3 and §9 item 6
("does closing a connection today tear down associated ARQ/session state,
or does it already survive independently?") — prior to this BC and this VP,
no connector existed to make that question answerable at all; this property
is the first place the answer becomes a checkable, proven fact rather than
an open design question.

## Proof Method

| Method | Tool | Bounded? | Coverage |
|--------|------|----------|----------|
| integration | `go test` against the connector under test, an `arq.ARQ` handle seeded with known in-flight entries, a `session.AccessNode` seeded with known console attachments, and a router fixture that can force a connection close mid-session and then accept a fresh admission on reconnect | yes | Two sub-cases: ARQ in-flight state identity across a forced reconnect; session/console-authorization state identity across the same forced reconnect |

**Method justification.** This property is a before/after state-equality
assertion spanning a stateful, multi-step lifecycle transition (live →
dialing → admitting → live again) across two collaborating components
(`internal/arq`, `internal/session`) that this BC's connector sits between
— not a pure-function property provable in isolation on either component
alone. Integration testing against the actual connector, `arq.ARQ` handle,
and `session.AccessNode` instance is the proof method that is falsifiable
against the real composition this BC wires together, mirroring VP-056's
own integration-test treatment of a structurally similar
"one component's lifecycle event must not disturb another's held state"
property (console detach not affecting other consoles' subscriptions).

### Test Scenarios

1. **ARQ survival:** seed `arq.ARQ` with N in-flight sequence numbers (via
   `EnqueueSend`) before the connector reaches *live*. Force a connection
   loss (close the underlying `net.Conn` from the test's own side, or have
   the router fixture close it). Let the connector reconnect (fresh dial +
   fresh admission against the same router fixture). Assert: for every one
   of the N sequence numbers, `InFlightContains` is still true and
   `PayloadForInFlight` returns the identical payload bytes, sampled
   immediately after the reconnect completes and before any new frame is
   sent.
2. **Session/console-authorization survival:** seed `session.AccessNode`
   with M console attachments (via `Attach`) and confirm each has a
   non-error authorization state, before the connector reaches *live*.
   Force the same connection-loss-and-reconnect sequence as scenario 1
   (same underlying connector instance; ARQ and session state are
   independent axes tested together for realism, asserted separately for
   clarity). Assert: all M attachments are still present and their
   authorization state is unchanged — no console was detached, evicted, or
   had to be re-attached, solely as a result of the wire reconnect.
3. **Connection IS torn down and re-derived (behavioral non-vacuity check —
   corrected v1.1, was a value-inequality check).** The original v1.0
   scenario asserted `envelopeBefore != envelopeAfter` as the negative-space
   check. That assertion is FALSE for a correct implementation reconnecting
   the SAME node identity: per the Property Statement 3 non-vacuity
   requirement above, `SVTNID` is invariant, `SrcAddr` is a deterministic
   function of `(SVTNID, pubkey)` (VP-014), and `FrameAuthKey` MUST be the
   same deterministic HKDF function of `(SVTNID, pubkey)` (ARCH-04,
   BC-2.05.010) — so `envelopeBefore == envelopeAfter` component-by-component
   is the CORRECT outcome, not a bug. Asserting inequality here would either
   make the property unprovable for a correct implementation, or pressure
   implementers into adding spurious per-handshake entropy to `FrameAuthKey`
   that would break router-side HMAC verification (see above). The
   non-vacuity purpose Scenario 3 exists for — proving the connector
   genuinely tore down and re-derived the envelope, rather than reusing a
   cached struct from before the connection loss — is instead proven
   behaviorally:
   - Assert the underlying `net.Conn` differs: capture `connBefore.LocalAddr()`
     and `connAfter.LocalAddr()` (the client's ephemeral TCP source port,
     assigned fresh by the OS on each `net.Dial`) and assert they differ —
     or, if the test harness exposes it, assert `connBefore != connAfter` by
     object identity. A stale-reuse bug would keep the OLD `net.Conn`, which
     this catches.
   - Assert a second, genuinely complete `NodeIdentify`/`Challenge`/
     `ChallengeResponse` exchange occurred: the router fixture records a
     handshake-completion counter (or the two `Challenge.Nonce` values it
     issued, which per BC-2.01.009 Postcondition 2/`admission.GenerateChallenge`
     are independently `crypto/rand`-sourced per handshake and therefore
     observably distinct across the two handshakes even though they do NOT
     feed `FrameAuthKey`); assert the counter is 2 (or the two nonces
     differ) after the reconnect. A stale-reuse bug would show only 1
     completed handshake.
   - Assert `envelopeAfter.SVTNID == envelopeBefore.SVTNID`,
     `envelopeAfter.SrcAddr == envelopeBefore.SrcAddr`, AND
     `envelopeAfter.FrameAuthKey == envelopeBefore.FrameAuthKey` — the
     CORRECT, expected outcome per the non-vacuity requirement, not a
     regression. `DstAddr` is asserted equal to its fixed zero-value
     placeholder on both sides (Non-Goals).

## Product-Owner Ruling: AC-006/AC-007 VP Coverage (v1.1)

Resolves the story's Residual Open Question 3 and the placement note's §8/§10
item 5 ("whether AC-006 [regular-send composition] and AC-007 [inbound
dispatch] warrant their own VPs beyond VP-081/VP-082's existing scope").

**Ruling: NO dedicated VP for either.** VP-081/VP-082's existing scope plus
the story's own planned unit/integration/race-detector tests are sufficient.
Rationale, by AC:

- **AC-006 (regular-send composition, BC-2.04.009 PC-4b).** The composition
  is a call-site discipline — `EnqueueSend` before `Assemble`+`Send`, for
  every tick including empty ones — over primitives that are ALREADY
  independently proven: `internal/arq`'s in-order/no-double-delivery
  properties are `VP-019`/`VP-020` (BC-2.02.005's own VP table cites these,
  not a call-site-composition VP); `internal/halfchannel`'s
  one-frame-per-tick and empty-frame-emission guarantees (the DI-008 source
  side) are `VP-016`/`VP-018`. What AC-006 adds beyond those is narrow —
  "don't drop the ticks you're handed" — directly covered by the story's own
  `TestAccessdial_RegularTickEmission_ReachesWire` (asserts both a data
  frame and an empty-tick frame reach the wire). The single-writer
  requirement (Invariant 3) is race-detector-verified
  (`TestAccessdial_Send_SingleWriterRace`, `go test -race`, AC-013) — no
  existing VP in VP-INDEX is shaped as "passes `-race`"; that is a
  build/CI-tool guarantee, not a property with a combinatorial input space
  warranting a dedicated VP.
- **AC-007 (inbound dispatch + EC-006 drop-on-miss, BC-2.04.009 PC-5).** A
  bounded two-outcome map lookup (`(SrcAddr, chan_id)` known vs. unknown),
  directly mirroring `BC-2.01.008` Postcondition 4's own silent-ignore
  precedent for unrecognized `control_type` values — and that BC's OWN
  Verification Properties table has NO dedicated VP for the silent-ignore
  behavior itself (only `VP-015`, an unrelated payload-independence
  code-audit note). Precedent: the exact behavioral pattern AC-007 mirrors
  was never VP-anchored at its origin. The story's own
  `TestAccessdialWire_ConsoleBinding_DispatchesToSendKeystroke` (hit) and
  `TestAccessdialWire_ConsoleBinding_MissDropsSilently` (miss) fully cover
  the bounded input space.
- **Governing precedent within this BC's own family.** `BC-2.09.003`'s
  Verification Properties table already establishes the pattern this ruling
  follows: PC-12 through PC-17 (simple, mechanically-checkable field
  validations) are ALL `test-as-evidence` rows with "no formal VP assigned"
  — only `VP-028`/`VP-029` (the earlier, narrower startup-validation
  properties) carry formal VP citations. AC-006/AC-007 fit the same
  shape — bounded, mechanically-checkable, adequately covered by directed
  tests — not the shape VP-081/VP-082 exist for (multi-message wire
  protocol exchanges and cross-component state-survival properties with
  larger, more consequential proof obligations).

No `VP-INDEX.md` change follows from this ruling (no new VP minted).
