# VP-081: Access-Node Connector Dial-Admit-First-Write Round Trip Completes; Handshake Failure Is Retryable, Not Fatal

## Property Statement

∀ startup (or post-reconnect) attempt of the access-node data-plane
connector (`internal/accessdial`, BC-2.04.009):

1. **Happy-path round trip.** Given a reachable configured router address
   and an Ed25519 admission keypair registered for the connector's target
   SVTN, the connector: (a) completes `net.Dial` to the router address;
   (b) sends `NodeIdentify`, receives and decodes `Challenge` (via the new
   client-side `decodeChallenge`), signs the nonce, and sends
   `ChallengeResponse` — the client-side half of BC-2.01.009's three-message
   exchange — without the router closing the connection; (c) performs a
   first successful frame write on the connection. The connector reaches
   its *live* state (BC-2.04.009 Postcondition 3) only after all three
   steps succeed, in order; no step is skippable or reorderable.
2. **Admission failure is retried, not fatal.** For every handshake-phase
   failure mode enumerated in BC-2.01.009's Error Codes table
   (unregistered key, revoked key, expired key, bad `NonceSig`, replayed
   nonce, malformed frame, handshake timeout, duplicate `NodeIdentify`,
   `ChallengeResponse` SVTNID mismatch) — each of which the router
   discharges as a bare connection close, per BC-2.01.009 Postcondition 10
   ("no error or status is returned to the connecting node beyond
   connection closure") — the connector: does not crash or exit the
   daemon process; logs the failure; and schedules a retry per its backoff
   policy (BC-2.04.009 Invariant 2). The connector's own state machine
   cannot distinguish "admission was rejected" from "the network dropped
   the connection at the same protocol phase" (BC-2.04.009 Invariant 5) —
   both are handled by the identical retry path.
3. **Private key never observed on the wire.** Across the full handshake
   (property 1) and every failure path (property 2), no byte sequence
   written to the connection, nor any log line emitted by the connector,
   contains the admission private key (DI-002; BC-2.04.009 Postcondition
   2d). Only the public key (in `NodeIdentify`) and the Ed25519 signature
   bytes (in `ChallengeResponse`) cross the wire.

This property enforces BC-2.04.009 Postconditions 1–3 (dial, handshake,
connection-established definition) and Invariants 1, 2, and 5 (private-key
non-transit, backoff-on-failure, admission-failure-is-retryable). It is the
access-node-side counterpart to BC-2.01.009's own router-side proof
obligations — BC-2.01.009 proves the router's handling of the three-message
exchange and its failure paths; this property proves the connector drives
that same exchange correctly from the other end and degrades gracefully
(never crash, never treat a rejection as fatal) when it doesn't complete.

## Source Contract

- **BC:** BC-2.04.009 — Access Node Dials Its Router, Completes Genuine
  NODE_IDENTIFY Admission, and Wires the Live ARQ Send-Path
- **Postcondition 1:** dial.
- **Postcondition 2:** client-side `NodeIdentify`/`Challenge`/
  `ChallengeResponse` exchange, including the new `decodeChallenge`
  function and the DI-002 private-key non-transit sub-clause (2d).
- **Postcondition 3:** the three-step "connection established" definition
  (dial → handshake → first write).
- **Invariant 2:** backoff-with-jitter on reconnect.
- **Invariant 5:** admission failure is wire-indistinguishable from network
  failure; both are retryable, neither is fatal.
- **Adjacent BC:** BC-2.01.009 (NODE_IDENTIFY Three-Message Handshake —
  Wire Protocol and Failure Paths) — the router-side counterpart this
  property's client-side exchange must interoperate with; its Error Codes
  table enumerates the handshake-phase failure modes property 2 covers.

## Proof Method

| Method | Tool | Bounded? | Coverage |
|--------|------|----------|----------|
| integration | `go test` against an in-process router fixture implementing BC-2.01.009's `onAccept` three-message handshake (or an equivalent admitted-node test harness), driving the connector over a real `net.Conn` pair (loopback TCP or `net.Pipe`) | yes | Three sub-cases: happy-path round trip to *live*; each handshake-phase failure mode retried without a fatal exit; private-key-absence audit across all wire bytes and log output produced during both sub-cases |

**Method justification.** This property is about a two-party wire exchange
(connector ↔ router) unfolding over time across three distinct messages,
not a single pure-function call — the same reasoning BC-2.01.009's own
`test-as-evidence` rows apply router-side, and the reasoning VP-064/VP-067
(management-plane handshake properties) already apply to this codebase's
other challenge-response exchanges. Integration testing against a real (or
loopback) `net.Conn` is the only proof method that is falsifiable without
presupposing the connector's internal state-machine representation, which
`internal/accessdial` does not yet have (new package, not yet implemented).

### Test Scenarios

1. **Happy path:** router fixture holds a registered, non-revoked,
   non-expired key matching the connector's keypair for the target SVTN.
   Drive the connector through dial → handshake → first write. Assert:
   `net.Dial` succeeds; `NodeIdentify` is well-formed per BC-2.01.009
   Postcondition 1; `Challenge` is correctly decoded by the new
   `decodeChallenge`; `ChallengeResponse`'s `NonceSig` verifies; the router
   fixture calls the equivalent of `BindInterface`; the connector's first
   frame write succeeds; connector state == *live*.
2. **Unregistered key:** router fixture returns `ErrNotAdmitted` from its
   `AdmitNode`-equivalent (closes the connection after `ChallengeResponse`,
   E-ADM-003). Assert: connector does not crash; retry is scheduled per
   backoff; connector state == *dialing* (not *live*, not a terminal error
   state).
3. **Bad `NonceSig`:** router fixture closes the connection after
   `ChallengeResponse` due to signature-verification failure (E-ADM-001).
   Assert: identical connector-side behavior to scenario 2 — the connector
   cannot and does not distinguish this failure from scenario 2 or from a
   plain network drop at the same phase.
4. **Handshake timeout:** router fixture accepts the TCP connection but
   never sends `Challenge`. Assert: connector's own handshake deadline (a
   value TBD at implementation, per BC-2.04.009 — not specified by this
   property) fires; connector treats this identically to scenarios 2–3.
5. **Plain network drop:** the underlying `net.Conn` is closed (or a read
   returns `io.EOF`/`io.ErrUnexpectedEOF`) at each of the three message
   boundaries, with no router fixture logic involved at all. Assert:
   connector behavior is identical to scenarios 2–4 — confirming Invariant
   5's wire-indistinguishability claim empirically, not just by
   specification reading.
6. **Private-key-absence audit:** across scenarios 1–5, capture every byte
   sequence written to the connection and every log line the connector
   emits. Assert: none contains the admission private key (a fixed known
   value in the test fixture, greppable byte-for-byte). This scenario
   deliberately reuses the audit shape of VP-007/VP-057 (private key never
   in wire structs / never in emitted frames), applied to this new
   connector's own I/O surface.
